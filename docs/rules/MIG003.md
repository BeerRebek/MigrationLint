# MIG003 — Column or table renamed

| | |
|---|---|
| **Category** | dataloss |
| **Default severity** | error (info when `deploymentStrategy` is `maintenance`) |
| **Triggers on** | `RenameColumn`, `RenameTable` |
| **Skipped when** | the target was created in this migration |

## Why this matters

A rename takes effect instantly. Every running instance of the previous application version is
still using the old name, so all of its queries against that column/table break the moment the
migration applies — a rolling deploy guarantees overlap.

## Bad

```csharp
migrationBuilder.RenameColumn(name: "Note", table: "Orders", newName: "Comment");
```

## Safe — expand/contract across three releases

1. **Release 1** — add the new column and dual-write to both old and new.
2. **Release 2** — backfill, then switch reads to the new column.
3. **Release 3** — stop writing the old column, then drop it.

## Suppressing

```csharp
[SuppressMigrationLint("Deployed in a maintenance window with no version overlap.", "MIG003")]
```

Teams that always deploy in a maintenance window can set `"deploymentStrategy": "maintenance"` to
downgrade this rule to info globally.
