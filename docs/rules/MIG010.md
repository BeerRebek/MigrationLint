# MIG010 — Schema changes mixed with data changes

| | |
|---|---|
| **Category** | locking |
| **Default severity** | warning |
| **Scope** | migration-level |
| **Triggers on** | ≥1 DDL operation **and** ≥1 data change in the same migration |

A "data change" is `InsertData`, `UpdateData`, `DeleteData`, or raw `Sql()` containing
`INSERT`/`UPDATE`/`DELETE`.

## Why this matters

DDL takes locks. When a data modification runs in the same migration transaction, it extends the
time those DDL locks are held — a slow `UPDATE` over millions of rows keeps a schema lock alive
for its entire duration, turning a quick schema change into a long outage.

## Bad

```csharp
migrationBuilder.AddColumn<string>(name: "Region", table: "Customers", nullable: true);
migrationBuilder.Sql("UPDATE \"Customers\" SET \"Region\" = 'unknown' WHERE \"Region\" IS NULL;");
```

## Safe

1. Apply the schema change in its own migration.
2. Move the data change to a separate migration, or to an idempotent background job that runs
   after deployment.

## Suppressing

```csharp
[SuppressMigrationLint("Customers has < 1k rows; the backfill is instant.", "MIG010")]
```
