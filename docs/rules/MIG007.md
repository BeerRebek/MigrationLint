# MIG007 — Index created without concurrent/online option

| | |
|---|---|
| **Category** | locking |
| **Default severity** | error |
| **Triggers on** | `CreateIndex` |
| **Skipped when** | new table · small table · provider is Sqlite or Unknown |

> This is MigrationLint's flagship rule. No other .NET migration tool checks for it.

## Why this matters

Building an index takes time proportional to table size, and by default the database holds a
lock that blocks writes for the **entire** build. On a large, actively-written table that is a
production write outage — the migration "succeeds", but the app is down while it runs.

Each engine has an online build option, but EF does not emit it by default:

- **PostgreSQL** — `CREATE INDEX CONCURRENTLY`. Cannot run inside a transaction.
- **SQL Server** — `WITH (ONLINE = ON)`. Requires Enterprise or Azure SQL.
- **MySQL/InnoDB** — online by default since 5.6, so this rule does not fire.

## Bad

```csharp
migrationBuilder.CreateIndex(
    name: "IX_Orders_Notes",
    table: "Orders",
    column: "Notes");
```

## Safe — PostgreSQL

```csharp
protected override bool SuppressTransaction => true; // CONCURRENTLY can't run in a transaction

migrationBuilder.CreateIndex(
        name: "IX_Orders_Notes", table: "Orders", column: "Notes")
    .Annotation("Npgsql:CreatedConcurrently", true);
```

Because `CREATE INDEX CONCURRENTLY` cannot run in a transaction, this index must be the **only**
operation in its migration.

## Safe — SQL Server

```csharp
migrationBuilder.CreateIndex(name: "IX_Orders_Notes", table: "Orders", column: "Notes")
    .Annotation("SqlServer:Online", true);
```

On Standard edition `ONLINE = ON` is unavailable — schedule the build in a maintenance window and
suppress this rule with a justification.

## Suppressing

```csharp
[SuppressMigrationLint("Orders is < 10k rows; brief lock is acceptable.", "MIG007")]
```

Or mark the table small in `migrationlint.json`:

```json
{ "options": { "smallTables": ["Orders"] } }
```
