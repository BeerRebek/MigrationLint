# MIG001 — Column dropped

| | |
|---|---|
| **Category** | dataloss |
| **Default severity** | error (warning when `deploymentStrategy` is not `rolling`) |
| **Triggers on** | `DropColumn` |
| **Skipped when** | column is on a table created in this migration |

## Why this matters

During a rolling deployment, instances running the previous version keep reading and writing the
column. The moment the column is dropped, those writes fail — the app throws until every old
instance is gone.

## Bad

```csharp
migrationBuilder.DropColumn(name: "LegacyNotes", table: "Orders");
```

## Safe — expand/contract across two releases

1. **Release 1** — stop reading and writing the column in application code (remove the property or mark it `[NotMapped]`).
2. **Release 2** — once Release 1 is fully rolled out, drop the column.

If the data may be needed later, rename to a quarantine name first and drop after a soak period.

## Suppressing

```csharp
[SuppressMigrationLint("Column removed from the entity in the previous release (v3.2).", "MIG001")]
```
