# MIG012 — Too many operations in one migration

| | |
|---|---|
| **Category** | hygiene |
| **Default severity** | warning |
| **Scope** | migration-level |
| **Triggers on** | `UpOperations.Count > options.maxOperationsPerMigration` (default 10) |

## Why this matters

A large migration runs as a single long transaction: it holds locks longer, takes longer to
apply, and cannot be rolled back partially — if operation 15 fails, you are left reasoning about
the state of the previous 14. Smaller migrations are safer to deploy and easier to reverse.

## Safe

Split into smaller migrations, each independently deployable and reversible. Order them so every
intermediate state is compatible with both the previous and the next application version.

## Configuring the threshold

```json
{ "options": { "maxOperationsPerMigration": 15 } }
```

## Suppressing

```csharp
[SuppressMigrationLint("Initial schema creation; splitting adds no safety.", "MIG012")]
```
