# MIG016 — Column added with a volatile default (forces a table rewrite)

| | |
|---|---|
| **Category** | locking |
| **Default severity** | warning |
| **Triggers on** | `AddColumn` with a volatile `defaultValueSql`, on PostgreSQL or SQL Server |
| **Skipped when** | new table; small table |

## Why this matters

Modern PostgreSQL and SQL Server can add a column with a **constant** default as a fast, metadata-only
change. But a **volatile** default — one that produces a different value per row — has to be
evaluated for every existing row, which rewrites the whole table under a lock.

Common volatile defaults: `now()`, `current_timestamp`, `gen_random_uuid()`, `uuid_generate_v4()`,
`random()`, `NEWID()`, `NEWSEQUENTIALID()`, `GETDATE()`, `RAND()`.

## Bad

```csharp
migrationBuilder.AddColumn<Guid>(
    name: "RowId", table: "Orders", nullable: false,
    defaultValueSql: "gen_random_uuid()");
```

## Safe

1. Add the column as nullable, with no default.
2. Backfill the value in batches (a background job, not this migration).
3. Set the default (and `NOT NULL`, if needed) once the backfill is complete.

## Suppressing

```csharp
[SuppressMigrationLint("Orders is small; the rewrite is cheap.", "MIG016")]
```
